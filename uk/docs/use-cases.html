Гнучкість DNIP​

DNIP може бути використаний у різних сценаріях:

  • у мікросервісній архітектурі,
  • у моноліті, який згодом можна розділити на кілька вузлів.

Використання у мікросервісах​

У мікросервісній системі кожен сервіс можна оформити як окремий Node:

  • Кожен має власний protocol.json, контракти та імплементацію.
  • Для комунікації між вузлами можна обрати потрібний транспорт (amqp, kafka, nats, redis, mqtt).
  • Gateway описує HTTP або RPC маршрути.
  • Завдяки уніфікованим контрактам легко інтегрувати нові вузли.

Приклад:

  • Сервіс user (керування користувачами).
  • Сервіс orders (керування замовленнями).
  • Сервіс billing (оплати).

Кожен з них є незалежним вузлом DNIP.

Використання у моноліті​

DNIP також може застосовуватися у монолітному додатку:

  • Усі сервіси описуються у єдиному protocol.json.
  • Імплементація містить увесь код у спільному проекті.
  • Gateway піднімає єдиний HTTP/RPC інтерфейс.

Цей підхід дозволяє почати з моноліту, але мати чітку декларацію API вже на старті.

Перехід від моноліту до мікросервісів​

Оскільки весь API описаний у protocol.json, розділити проект на вузли просто:

  1. Витягуємо частину дій у новий protocol.json.
  2. Переносимо відповідні контракти та імплементацію.
  3. Підключаємо вузол у спільну мережу DNIP.

DNIP гарантує, що API не зламається при такому розділенні.

Висновок​

  • DNIP може слугувати єдиним стандартом і для моноліту, і для мікросервісної архітектури.
  • Це спрощує еволюцію проекту: від початкової монолітної системи до розподіленої мережі вузлів.
